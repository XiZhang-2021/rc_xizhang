# API 通知系统

本项目用于 AI Coding 作业：设计一个内部服务，接收业务系统提交的外部 HTTP(S) 通知请求，并尽可能可靠地投递到目标地址。

当前处于需求分析阶段，尚未编写业务代码。下述方案是待确认的设计建议，不代表已经实现的能力或已由项目作者作出的最终决策。

## 需求理解

多个内部业务系统需要向不同外部供应商发送通知。供应商的请求地址、Header 和 Body 格式可能不同。业务系统无需同步获取供应商的业务结果，但需要通知服务可靠地保存请求并负责后续投递。

作业要求交付最小可行实现、README 或设计文档，以及真实的 AI 使用说明。设计需解释系统边界、投递语义、失败处理、工程取舍和未来演进。语言、技术栈和是否使用消息队列均未限定。

## 建议的系统边界

第一版建议由调用方构造完整的 HTTP 请求，通知服务负责校验、持久化、异步投递、失败重试和状态查询。

建议包含：

- 接收目标地址、请求方法、Header 和 Body，并限制请求大小和允许访问的目标。
- 持久化成功后确认接收，返回任务标识。
- 后台投递，设置超时，记录投递状态和必要的错误信息。
- 对可恢复失败延迟重试，达到次数或时间上限后保留终止失败记录。
- 服务重启后恢复未完成任务。
- 基本调用鉴权和敏感信息脱敏。

建议暂不包含：

- 供应商专属的字段映射、签名、令牌刷新和业务响应解析。
- 业务工作流、跨系统事务、严格顺序保证。
- 完整管理后台、多租户配额和跨地域容灾。

这些边界用于控制 MVP 复杂度；若存在必须支持的供应商协议，应重新评估。

## 可靠性与失败处理

接收成功、投递成功和外部业务执行成功是不同的概念。建议以持久化成功作为接收成功，以符合约定的 HTTP 成功响应作为投递成功；外部业务是否实际完成，取决于供应商协议。

服务仅从持久化接收成功开始承担投递责任。业务事件发生后、请求提交前的丢失风险由调用方处理；未来可根据需要在调用方引入事务性 Outbox。

建议采用允许重复投递的重试策略，不承诺外部业务效果恰好发生一次。外部系统可能已经完成操作，但响应丢失，导致通知服务重试。若使用“至少一次”描述投递语义，必须说明成立条件：有限重试无法保证永久不可用的目标最终收到通知。

需要区分两类幂等：

- 提交幂等：调用方重复提交同一请求时，使用调用方提供的唯一标识避免重复创建任务。
- 下游业务幂等：重复投递不能产生重复业务副作用，需要外部系统支持。若支持幂等键，各次重试应使用同一个键。

建议的默认失败策略：

| 情况 | 处理建议 |
| --- | --- |
| 符合约定的成功响应 | 标记成功 |
| 网络异常、超时、可恢复的服务端错误 | 延迟重试 |
| 限流响应 | 延后重试，考虑对方提供的等待时间 |
| 明确的参数或权限错误 | 停止自动重试，保留原因 |
| 超过重试次数或时间上限 | 标记终止失败，保留记录供后续处理 |

重试间隔建议逐步增加并加入随机扰动。任务领取和处理中状态需要可恢复机制，避免进程崩溃后任务永久卡住。状态查询、失败记录保留和人工重放的具体范围尚待确定。

## 待确认的关键决策

1. 是否由调用方构造完整 HTTP 请求，是否存在必须支持的供应商适配逻辑？
2. 成功是否统一按 HTTP 状态判定，还是需要解析特定业务响应？
3. 下游是否支持幂等，重复操作会造成什么影响？
4. 重试次数和期限是多少，终止失败由谁处理？
5. 是否要求顺序、时延、吞吐量或特定部署方式？
6. 请求唯一标识的作用域、保留期限和冲突处理规则是什么？

## 方案取舍与演进方向

尚未选择技术栈或中间件。可以比较“数据库任务表 + 后台工作进程”和“消息队列 + 消费者”：前者依赖较少，后者需要说明引入队列后带来的收益，以及持久化与入队之间的一致性如何处理。

在没有规模证据前，不把多种中间件、供应商插件平台或复杂分布式调度作为 MVP 前提。未来根据实际瓶颈考虑增加工作进程、按供应商限制并发、隔离故障目标、引入消息队列或扩展供应商适配能力。

这些是候选方案和讨论方向，尚不能记为作者已经采纳或拒绝的设计。

## 后续验收重点

- 已确认接收的任务在重启后仍然存在，并能继续处理。
- 外部服务暂时失败后按策略重试，并记录最终状态。
- 永久失败达到上限后停止自动重试，原因可查询。
- 重复提交按幂等约定处理，重复投递的限制有明确说明。
- 慢请求有超时，不会无限占用处理资源。
- 日志不会泄露认证 Header 等敏感信息。

以上为计划中的验收场景，尚未实现或执行测试。
